## Base URL

By default, DBX Web listens on port `4224`:

```text
http://localhost:4224
```

When deployed behind a reverse-proxy subpath, set `DBX_PUBLIC_BASE_PATH` and prefix every route. For example, with `/dbx`:

```text
https://example.com/dbx/api/auth/check
```

All API routes are under `/api`.

## Authentication

Protected routes require a session cookie named `dbx_session`.

### Check Auth State

```http
GET /api/auth/check
```

Example response:

```json
{
  "authenticated": false,
  "required": true,
  "setup_required": false
}
```

| Field | Meaning |
| --- | --- |
| `required` | Password protection is enabled |
| `setup_required` | First-run password setup is still needed |
| `authenticated` | Current request already has a valid session |

### First-Run Setup

```http
POST /api/auth/setup
Content-Type: application/json

{
  "password": "your-password",
  "setup_token": "value of DBX_SETUP_TOKEN when configured"
}
```

Setup is only accepted while no local user exists. When `DBX_SETUP_TOKEN` is set, the request must carry it; configure it before exposing a fresh instance, otherwise the first visitor becomes administrator.

### Login

```http
POST /api/auth/login
Content-Type: application/json

{
  "password": "your-password",
  "email": "optional local user email; defaults to admin"
}
```

On success, the response sets `Set-Cookie: dbx_session=...`. Reuse that cookie on later requests.

Five consecutive login failures for one account **from the same client address** trigger an approximately 60-second lockout; other accounts and other clients are unaffected. Cross-origin browser writes are rejected unless the `Origin` host matches the request `Host`; non-browser clients send no `Origin` and are unaffected. Sessions are persisted in `dbx.db`, so a restart does not log everyone out; they expire after 30 minutes idle (`DBX_SESSION_IDLE_SECS`) or 24 hours absolute (`DBX_SESSION_TTL_SECS`), and a password change revokes every other session. Only the SHA-256 hash of a session token is stored. The cookie is `HttpOnly`, uses `SameSite=Lax`, and follows `DBX_PUBLIC_BASE_PATH` for its path.

`GET /api/auth/check` returns the signed-in actor's roles and effective permission codes (`audit:read`, `query:write`, …). The UI uses them to hide actions; the server still enforces each one.

### Logout

```http
POST /api/auth/logout
Cookie: dbx_session=...
```

| `DBX_AGENT_DIR` | Override the Web Agent/driver directory; defaults to `agents` under the data directory |
| `DBX_STATIC_DIR` | Override the Web static asset directory |

| `RUST_BACKTRACE=1` | Include Rust backtraces when an error reports one |

## Logging and Troubleshooting

DBX Web reads the standard `RUST_LOG` filter when it starts. For a focused diagnostic run, increase the Web and HTTP middleware targets without enabling every dependency:

```bash
RUST_LOG=dbx_web=debug,tower_http=info ./dbx
```

Set `RUST_BACKTRACE=1` as well when the error includes a Rust backtrace. If the problem is inside another DBX crate, add its target to the same filter, such as `dbx_core`, `dbx_drivers`, `dbx_sql`, `dbx_plugin_runtime`, `dbx_ai_provider`, or `dbx_platform`. `RUST_LOG=debug` enables a much broader and noisier filter. Logs are written to the process output; redirect that output when you need to save a diagnostic file.

## Request Format

- Field naming follows each Rust request type. Some bodies use `camelCase`, while connection configuration still contains `snake_case`; do not apply one naming convention to the whole API.
- `GET` query parameters commonly use `snake_case`, such as `connection_id`, but the current route implementation remains authoritative.
- Errors usually return JSON with an `error` field and an HTTP status code.
- Long-running export, import, transfer, SQL-file, and AI operations commonly use a start request plus SSE progress and cancel/download routes rather than one synchronous response.

Only the data-grid extractor currently exposes a tested, scoped OpenAPI document at `/api/query/data-grid-extractor-openapi.json`. It does not cover the complete DBX Web API or version the other routes.

### Read Oracle-Family Triggers

To find triggers without knowing their owning table, use the object list with a
trigger type filter. Search and type filters are applied before paging in the
exact metadata adapters.

```http
GET /api/schema/objects?connection_id=CONNECTION_ID&database=demo&schema=APP&object_types=TRIGGER&filter=audit&limit=100&offset=0&identity_mode=exact
Cookie: dbx_session=...
```

Use the owning object's schema and name to list its triggers. The returned
trigger owner can differ from that schema.

```http
GET /api/schema/triggers?connection_id=CONNECTION_ID&database=demo&schema=DATA&table=ORDERS&identity_mode=exact
Cookie: dbx_session=...
```

Fetch the full definition using the **trigger's** owner and name. On this route,
`table` is the source object name, not its parent table.

```http
GET /api/schema/object-source?connection_id=CONNECTION_ID&database=demo&schema=APP&table=AUDIT_ORDERS&object_type=TRIGGER&identity_mode=exact
Cookie: dbx_session=...
```

These three routes accept optional `identity_mode=exact` and `catalog` query
parameters. Omitting `identity_mode` retains the existing metadata behavior.
Exact reads preserve raw owner/name values; URL-encode spaces, quotes, and other
reserved characters rather than trimming or changing their case. `catalog` is
forwarded to the selected metadata provider; it does not replace `schema`.

Trigger summaries and source responses may contain `trigger.oracle_metadata`
(`oracle_metadata` directly on entries returned by `/schema/triggers`). Version
1 includes the verified engine, exact owner/name, scope, independent parent,
string-valued object ID, and per-field `reads` states. `enabled` is the trigger
state; `valid` is the independently read object validity. Schema/database scopes
do not have an invented table parent.

An exact source lookup that succeeds with no visible matching trigger returns
`reads.identity.state="empty"` with the verified engine and raw target. It means
empty within current visibility, not global absence. Query failures and legacy
providers cannot supply that proof; creation still uses CREATE without REPLACE.

Source metadata additionally reports definition origin/format/completeness and
compilation errors with line/position. A null or absent error list is unknown,
not an empty successful read. Failed or incomplete reads cannot supply a write
baseline; keep the draft, restore dictionary access or update the provider, and
read again. Old Agents/plugins that omit the metadata contract remain usable in
their original mode but do not prove exact identity. The source text can include
a same-target state appendix from `DBMS_METADATA`; it is export text, not an
arbitrary multi-statement save payload.

Other schema routes include:

- `/api/schema/databases`
- `/api/schema/schemas`
- `/api/schema/indexes`
- `/api/schema/foreign-keys`
- `/api/schema/ddl`

## SQL Query APIs

### Execute One Statement

```http
POST /api/query/execute
Content-Type: application/json

{
  "connectionId": "connection-id",
  "database": "app",
  "sql": "select id, name from users limit 10"
}
```

Example response shape:

```json
{
  "columns": ["id", "name"],
  "rows": [[1, "Ada"], [2, "Lin"]]
}
```

Related routes:

| Route | Purpose |
| --- | --- |
| `/api/query/execute-multi` | Execute multiple result sets in one request |
| `/api/query/execute-batch` | Execute a list of statements |
| `/api/query/cancel` | Cancel a running query |
| `/api/query/build-table-select-sql` | Build a table browse query |

### Prepare One Oracle-Family Trigger Definition

`POST /api/query/prepare-oracle-trigger-sql` accepts `{ "input": ... }` with
`databaseType` (`oracle`, `oceanbase-oracle`, or `dameng`), raw `owner`/`name`,
`source`, and `purpose` (`inspect`, `create`, or `replace`). It returns a single
normalized `definition`, the parsed `header`, and independent inline/export
enabled states. This route only prepares SQL; execute through the normal query
route after checking the current object, privileges, and concurrent changes.

`comparisonSource` is for readback comparison only. It canonicalizes the known
declaration wrapper while preserving the remaining header, body, comments, and
literal newlines. Execute `definition`, not this comparison form.

`structuredEditable` reports whether the complete definition's header can be represented without loss by the timing/event/body form. A false or absent value requires the complete-source editor for structural changes; a plain `TRIGGER_BODY` alone does not establish this capability.

For create/replace, supply `binding` with the verified `scope`
(`TABLE`, `VIEW`, `SCHEMA`, `DATABASE`, or `TIMER`), parent `owner`/`name` where
applicable, and `pluggable` for a verified Oracle container scope. Omitted ON
qualifiers are filled only from that binding. Replace also requires the current
desired `enabled` state. Create produces CREATE without OR REPLACE. Oracle and
verified OceanBase preserve state in the definition; DM's
`requiresStateRestore` indicates a separate native state step to preview and
verify. `allowExportAppendix` is only for inspecting trusted metadata exports;
write purposes reject it and any extra SQL.

## Writes, Safety, and File Boundaries

- API authentication proves only that the request belongs to a logged-in session; it does not replace database privileges
- Query, import, and transfer paths continue to enforce connection read-only protection, while production and SQL-risk policy apply in their corresponding core paths
- Browser-selected table-import and SQL files are uploaded into server temporary storage, not read from arbitrary client paths
- Web exports create a temporary server file, return it through a download route, and then clean it up
- Reverse proxies should preserve cookies and SSE streaming, allow appropriate long-running timeouts, and limit public exposure

### hilbert / ongrid tokens

With `DBX_HILBERT_ENABLED=1`, an `Authorization: Bearer <access token>` header
authenticates the request without a DBX session cookie. The token is verified on
every request, so disabling the account in hilbert takes effect immediately.

Accepted tokens must declare `aud=dbx`, `iss=ongrid`, and `token_type=access`;
refresh tokens and tokens without a type are rejected. Before enabling this,
hilbert must be configured with its own `ONGRID_SECRET_KEY` and a DBX-specific
key: when the vault key is derived from `ONGRID_JWT_SECRET`, sharing that secret
with DBX would also expose hilbert's encrypted credentials. DBX refuses HS256
unless `DBX_HILBERT_ALLOW_SHARED_SECRET=1` is set for a transition; RS256 with a JWKS
endpoint or a PEM public key is the supported configuration. Keys are fetched
once at startup, so restart after a hilbert key rotation.

Roles map conservatively: `is_superuser` → `admin`, `role=admin|owner` →
`admin`, `dba`/`security_admin`/`auditor`/`operator` map to the same DBX role,
and anything else is `viewer` until `/v1/me` membership resolution exists.

### Governance simulation

```http
POST /api/governance/simulate
Content-Type: application/json

{
  "connection_id": "conn-id",
  "database": "app",
  "sql": "DELETE FROM users"
}
```

Returns the strictest matched rule (`allow` / `warn` / `require_approval` /
`block`), every matching rule, whether the connection is production, and whether
enforcement is on. It requires `query:read` and never executes the statement.

Built-in rules (code-defined for now):

| Rule | Effect |
| --- | --- |
| `prod.ddl.approval` | Production DDL needs approval |
| `prod.dml.no_where.block` | Unbounded write on production is blocked |
| `prod.truncate.approval` | Production `TRUNCATE` needs approval |
| `prod.privilege.approval` | Production `GRANT`/`REVOKE`/`CREATE USER` needs approval |
| `global.no_where.warn` | Unbounded write warns anywhere |
| `global.ddl.warn` | DDL warns outside production |

With `DBX_GOVERNANCE_MODE=enforce`, a `block` decision returns
`POLICY_DENIED` and `require_approval` returns `POLICY_APPROVAL_REQUIRED`
before the statement reaches a driver; both are audited (`blocked` /
`approval_required`). The default `observe` mode records nothing new and keeps
execution unchanged.

### Route permissions

Every API prefix maps to a permission (`query:write` for SQL execution,
`connection:read` for listing connections, `export:data` for exports, …). The
server checks it after authenticating the session:

- `observe` (default): the check runs but unclassified routes are still served,
  so an existing deployment keeps working while the table is completed.
- `enforce`: a missing permission returns `403 PERMISSION_DENIED`; a route with
  no classification requires `admin:settings` and otherwise returns
  `403 ROUTE_PERMISSION_UNCLASSIFIED`. New routes must be added to the table in
  `crates/dbx-web/src/route_permissions.rs` before regular users can call them.

`/api/audit/*` has its own gate (permission, bootstrap token, or loopback), and
`/api/auth/*` is handled by the login endpoints.

## Connection Groups

Connection groups are server-owned and are the only authorization scope for
connections; the sidebar layout is presentation only. All endpoints require
`admin:users`.

```http
GET  /api/connection-groups
POST /api/connection-groups            { "name": "prod", "parent_id": null }
PUT  /api/connection-groups/{id}       { "name": "prod", "parent_id": null }
DELETE /api/connection-groups/{id}
PUT  /api/connection-groups/{id}/members { "connection_ids": ["conn-a", "conn-b"] }
```

A group cannot be nested under its own descendant, cannot be deleted while it
has children or a role binding references it, and child groups inherit a parent
binding's scope at authorization time.

## Policy Documents

Rules are compiled from the built-in safety floor plus the latest published
document of every scope (`global`, `connection:<id>`, `database:<name>`). The
compiled set carries a `policy_bundle_hash`; audit events and approvals bind to
it, so publishing a policy invalidates outstanding approvals.

```http
GET  /api/policies?scope_type=global
POST /api/policies
{
  "scope_type": "connection",
  "scope_id": "conn-id",
  "note": "block deletes on this connection",
  "document": {
    "rules": [
      { "id": "conn.deny-deletes", "priority": 200, "action": "block",
        "message": "deletes are blocked here",
        "match": { "statement_types": ["dml"] } }
    ]
  }
}

POST /api/policies/rollback
{ "scope_type": "global", "version": 2, "note": "revert" }

GET /api/policies/effective
```

- Versions are immutable per scope; rollback publishes a copy of an old
  version as a new one.
- A stored rule with the same `id` as a built-in replaces it (use
  `"enabled": false` to disable a built-in).
- Evaluation takes the strictest effect across all applicable scopes, so a
  narrower scope can only tighten a broader one.
- Publishing is refused if the document does not parse or would produce an
  invalid rule set; the effective policy is only replaced after a successful
  publish.
- Reads require `policy:read`; publish/rollback require `policy:publish`.

`GET /api/governance/simulate` and `GET /api/policies/effective` include the
`policy_bundle_hash` used for the decision. The security settings page has a
policy editor: choose a scope, edit the JSON document, publish, review versions,
and roll back. A database scope of `<connection_id>::<database>` pins both.

## Approvals

Statements the rules mark `require_approval` cannot run until an approver decides
a request. Requests are bound to the exact statement, connection configuration,
schema, policy bundle, and rule IDs; changing any of them invalidates the token.

```http
POST /api/approvals
{
  "connection_id": "conn-id",
  "database": "app",
  "sql": "ALTER TABLE users ADD COLUMN age int",
  "justification": "add age column"
}

GET  /api/approvals?mine=1&status=pending
GET  /api/approvals/{id}
POST /api/approvals/{id}/approve   {"comment": "ok"}
POST /api/approvals/{id}/reject    {"comment": "no"}
POST /api/approvals/{id}/execute-token

GET    /api/approval-templates
POST   /api/approval-templates
       {"name": "Prod DDL", "scope_type": "connection", "scope_id": "conn-id",
        "steps": {"steps": [{"mode": "any", "roles": ["dba"], "users": []},
                            {"mode": "all", "roles": ["security_admin"], "users": []}]}}
PUT    /api/approval-templates/{id}
DELETE /api/approval-templates/{id}
```

- Creating a request requires `query:write` and at least one rule with
  `require_approval`.
- Listing requires `approval:read`; approving, rejecting, and issuing a token
  require `approval:act`.
- The requester cannot decide their own request.
- Requests follow an approval template's steps in order. `any` steps need one
  approval; `all` steps are countersigned by every user snapshotted for the
  step. A rejection closes the request and skips the remaining steps. A
  connection template wins over a global one; `template_id` in the create body
  overrides the resolved template. Without a template the built-in single step
  lets any holder of `approval:act` decide.
- `GET /api/approvals?assigned=1&status=pending` returns only requests whose
  current step the caller may decide. `GET /api/approvals/{id}` returns the
  steps and recorded votes; it is limited to the requester, administrators, and
  actors who may decide a step.
- Only the requester can obtain the execution token, only after approval, and
  only once per token store; the raw token is returned once and expires after 5
  minutes. Execution must present it together with the same binding.
- An approved DDL token also satisfies the resource scope: a role with
  `query:write` but without `query:ddl` may execute the approved statement.
  Rules are re-evaluated first and the token is consumed only after the scope
  check passes.
- `approval.created`, `approval.step_pending`, `approval.step_approved`,
  `approval.approved`, and `approval.rejected` are delivered to every configured
  channel: the generic webhook (signed with `x-dbx-approval-signature` when
  `DBX_APPROVAL_WEBHOOK_HMAC_KEY` is set), DingTalk, and Feishu/Lark. Chat
  channels get a short text summary; the payload never contains SQL text.
  Delivery is best-effort and retries are not implemented.
- For a script/batch, pass `statements` (the server-side split list) when
  creating the request; the token then binds the complete ordered list and is
  sent as `X-DBX-Approval-Token` on `/api/query/execute-script` or
  `/api/query/execute-multi`, including `use_transaction` batches. A `block`
  anywhere still stops the batch.

The query path consumes the token: it re-evaluates every rule (a `block` still
wins), verifies the binding, marks the token used, and only then executes the
authorized statement list. A spent token cannot be replayed, and changing the
SQL, connection configuration, or published policy invalidates it.

### Retention and segment deletion

`DBX_AUDIT_RETENTION_DAYS` only warns. Deleting a retained prefix is explicit:

```http
POST /api/audit/retention/prune
{ "up_to_seq": 1000, "reason": "archived to SIEM" }
```

Pruning requires `audit:verify`, `DBX_AUDIT_ALLOW_PRUNE=1`, a checkpoint at or
above the cutoff, and an external export covering it; otherwise it fails with
`AUDIT_PRUNE_CHECKPOINT_REQUIRED` / `AUDIT_PRUNE_EXPORT_REQUIRED`. The last
deleted hash becomes the chain floor: `/api/audit/verify` starts there, and the
pruning itself is recorded as a maintenance audit event. The live tail can
never be deleted.

## Users and Roles

Local users replace the single shared password. Each user has one built-in role
at global scope; every response carries the effective permission codes.

```http
GET /api/users
POST /api/users
PATCH /api/users/{user_id}
POST /api/users/{user_id}/password
GET /api/users/{user_id}/sessions
DELETE /api/users/{user_id}/sessions/{session_id}
POST /api/users/{user_id}/sessions/revoke
GET /api/roles
POST /api/roles
PUT /api/roles/{code}
DELETE /api/roles/{code}
```

```json
{
  "email": "dba@example.com",
  "display_name": "Ops DBA",
  "password": "at-least-8-characters",
  "role": "dba",
  "scope": { "scope_type": "connection_group", "scope_id": "group-id" }
}
```

`scope` defaults to `global`. A `connection` scope names one connection; a
`connection_group` scope covers the group's connections and all descendant
groups. A scoped binding only authorizes connections inside its scope, so the
same role can be granted per team without a global grant. A `database` scope
uses `scope_id` of the form `<connection_id>::<database>` and matches only that
database on that connection.

All routes require `admin:users`. Disabling a user, changing their role, or
resetting their password revokes their live sessions. The built-in `admin` user
cannot be disabled or moved off the `admin` role. `PATCH` also accepts
`display_name`.

Custom roles are created with a code (1-64 chars of `[a-z0-9_.-]`, not a
built-in code), a name, and a list of permission codes; built-in roles cannot be
edited or deleted, and a role still bound to users cannot be deleted. Editing a
role's permissions signs out every user bound to it so the change takes effect
immediately. Role sessions are listed per user (id, timestamps, client address,
user agent) and can be revoked individually or all at once.

| Role | Capabilities |
| --- | --- |
| `admin` | Everything |
| `security_admin` | Policies, approvals, audit; cannot execute SQL |
| `dba` | Execute and approve within scope, including DDL; can read audit |
| `auditor` | Read, export, and verify audit; cannot execute SQL |
| `operator` | Read/write SQL within scope; DDL needs approval |
| `viewer` | Read-only queries |

## Audit APIs

Server-side audit records every SQL execution and the authentication/config
events around it. Events are append-only and hash-chained; every response here
is read from the chain itself, not from a mutable history table.

In the Web server the log lives in its own SQLite file (`<data_dir>/audit.db`,
override with `DBX_AUDIT_DB_PATH`), so audit I/O never contends with the UI's
storage lock. Desktop, CLI, and local MCP keep the log in their existing
database file. Moving a pre-`audit.db` deployment means migrating the
`audit_*` tables together with their chain head; do not copy rows between chains.

<Callout type="warn">A signed-in session holding the required permission (`audit:read`, `audit:export`, or `audit:verify`) is accepted. Otherwise the request must carry `X-DBX-Audit-Token` matching `DBX_AUDIT_BOOTSTRAP_TOKEN`, or arrive over loopback when no token is configured. The bootstrap token works without a session, for automation; those requests are attributed to the `system` actor. Deployments behind a reverse proxy on the same host see loopback peers, so they must set `DBX_AUDIT_BOOTSTRAP_TOKEN`.</Callout>

```http
GET /api/audit/events
X-DBX-Audit-Token: <DBX_AUDIT_BOOTSTRAP_TOKEN>
```

Query parameters: `actor_id`, `connection_id`, `database`, `operation`,
`decision`, `outcome`, `sql_contains`, `from_ms`, `to_ms`, `cursor_seq`,
`limit` (max 500).

```http
GET /api/audit/events/{event_id}
GET /api/audit/stats?from_ms=...&to_ms=...
GET /api/audit/chain-head
GET /api/audit/checkpoints
POST /api/audit/checkpoint
GET /api/audit/verify?from_seq=1
GET /api/audit/verify-checkpoint
GET /api/audit/export?format=jsonl
GET /api/audit/export?format=csv
```

`/api/audit/verify` recomputes each row's hash under the scheme stored with that
row (`sha256-v1` for rows written before the canonical form was extended,
`sha256-v2` afterwards) and reports the first broken sequence number for a
modified row, a deleted tail, a rolled-back head, a deleted head, or a gap.

`/api/audit/verify-checkpoint` starts from the newest checkpoint instead of
genesis, so tampering with the head of an old chain still fails against the
retained anchor. Checkpoints are signed with `DBX_AUDIT_CHECKPOINT_KEY` when
set; keep that key outside the database and back it up separately.

Reads and exports are themselves recorded as audit events with
`details.meta = true`.

### External audit export

Set `DBX_AUDIT_EXPORT_URL` (and preferably `DBX_AUDIT_EXPORT_HMAC_KEY`) to push
the log to a collector, SIEM, or a WORM-backed endpoint. Every batch is a JSON
envelope:

```json
{ "from_seq": 100, "to_seq": 199, "count": 100, "events": [ ... ] }
```

`x-dbx-audit-signature: sha256=<hmac-sha256 of the exact body>` lets the receiver
reject tampering in transit. Delivery is at-least-once and resumes from the last
acknowledged sequence (`audit_export_state`); deduplicate on `event_id`. A
failed delivery leaves the cursor unchanged and retries on the next tick.

Set `DBX_AUDIT_EXPORT_POSTGRES_URL` (and optionally
`DBX_AUDIT_EXPORT_POSTGRES_TABLE`, default `dbx_audit_events`) to write batches
into PostgreSQL instead; when both sinks are configured, PostgreSQL wins. Each
event becomes one row (`seq`, `event_id`, `occurred_at`, `actor_id`,
`event_hash`, `prev_hash`, `body` JSONB) and `ON CONFLICT DO NOTHING` makes
retries idempotent. The exporter connects over TLS with the system trust store
and creates the table on first use. SLS/OSS are best fed by a collector behind
the HTTP sink; the exporter does not sign vendor APIs itself.

### Audit environment variables

| Variable | Default | Meaning |
| --- | --- | --- |
| `DBX_AUDIT_MODE` | `on` | `off` disables the writer; not permitted together with fail-closed enforcement |
| `DBX_AUDIT_SQL_MODE` | `full` | `full`, `redacted`, or `digest` retention for the statement text |
| `DBX_AUDIT_MASK_CREDENTIALS` | `1` | Masks password/token literals even in `full` mode |
| `DBX_AUDIT_BOOTSTRAP_TOKEN` | unset | Token required by the audit API when set; otherwise loopback only |
| `DBX_AUDIT_CHECKPOINT_KEY` | unset | HMAC key for checkpoint signatures |
| `DBX_AUDIT_RETENTION_DAYS` | `180` | Warn when the oldest event is older than this; `0` disables the warning. Deletion is always manual |
| `DBX_AUDIT_DB_PATH` | `<data_dir>/audit.db` | Dedicated audit database file |
| `DBX_AUDIT_EXPORT_URL` | unset | Push signed JSONL batches to this endpoint every 10s |
| `DBX_AUDIT_EXPORT_POSTGRES_URL` | unset | Write batches to PostgreSQL instead of the HTTP sink (TLS required) |
| `DBX_AUDIT_EXPORT_POSTGRES_TABLE` | `dbx_audit_events` | Destination table (`table` or `schema.table`) |
| `DBX_AUDIT_ALLOW_PRUNE` | unset | `1` enables `POST /api/audit/retention/prune` |
| `DBX_AUDIT_EXPORT_HMAC_KEY` | unset | HMAC key for the `x-dbx-audit-signature` header (`sha256=<hex>`) |
| `DBX_TRUSTED_PROXIES` | unset | Comma-separated proxy IPs allowed to supply `X-Forwarded-For` |
